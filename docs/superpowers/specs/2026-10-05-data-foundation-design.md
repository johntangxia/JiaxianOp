# 数据基础（频道体系与模拟真实度）· 设计方案

- 日期：2026-10-05
- 状态：待实施（实施计划见 [数据基础](../plans/2026-10-05-data-foundation.md)）
- 前置依赖：九份基础计划全部完成。本计划是"运营分析增强"路线图（计划 10–16）的第一步，后面的频道驾驶舱、竞赛榜、下钻、读者侧分析、增长闭环都建立在这里产生的数据上。

## 1. 背景与目标

稼先社区的形态类似今日头条：顶部导航里**综合频道**（关注、推荐、热点、视频、直播）和**领域频道**（AI学习、半导体、无线……）平级，每个频道都有自己的入口和信息流；内容只产生在领域频道，综合频道只做分发。现有模拟数据离这个形态很远：只有 15 个频道且类别混乱，员工部门是旧的 9 个名字，内容随机落在任意频道，所有员工从第一天起就在社区里，行为随机均匀。

本计划把数据基础打牢，让后续的分析"有东西可分析"：

1. 频道体系换成 5 个综合频道 + 23 个领域频道，内容只落在领域频道。
2. 员工归属领域（`dept` = 领域频道名），并有"加入社区日期"。
3. 行为模拟加入留存分型、周末/工作时段规律、热度衰减、同领域偏好、沉默读者（只看不互动）。

不做：曝光/入口/来源（计划 11）、任何新的分析接口和页面（计划 12 起）。

## 2. 频道体系

| 类别 | 值 | 频道 |
|---|---|---|
| 综合频道 | `综合频道` | 关注、推荐、热点、视频、直播 |
| 领域频道 | `领域频道` | AI学习、终端、智能汽车、半导体、无线、云核、AI研发、自动驾驶网络ADN、交付服务、服务软件、华为云、光、数通、数据存储、计算、知识产权、制造、供应链、战略、能源、质量、海外研究所、2012 |

- `data.sql` 种子改为这 28 个频道（幂等）。
- **旧库升级**：`data.sql` 里幂等地把旧的 `专业领域` 类别和 `AI学习` 改成 `领域频道`；旧种子里已经不存在的频道（移动无线、固定网络、IT计算）没有内容引用就删除，有引用就把类别置为 `已停用`；下次历史回填清空内容后，顺带删掉 `已停用` 的频道。
- `Channel` 实体增加常量 `CATEGORY_COMPOSITE` / `CATEGORY_DOMAIN`。`ChannelRepository` 增加 `findByCategory`、`deleteByCategory`。
- 内容生成只用 `领域频道`；没有领域频道时抛出明确的异常，而不是静默用综合频道。
- 前端总览的频道筛选只列领域频道（PV 按内容所属频道统计，综合频道没有内容）。后端 `/api/dimensions/channels` 仍返回全部频道及类别。

## 3. 员工与"加入社区日期"

**新字段** `employee.community_join_date DATE`（"首次进入社区的日期"，不是公司入职日；原有的 `join_date` 保持原义不动）。

- **旧库升级**：这个库没有迁移工具，`ADD COLUMN IF NOT EXISTS` 在 OpenGauss 里不支持。新增 `SchemaUpgrader`（`InitializingBean`），启动时检查 `information_schema`，缺列就 `ALTER TABLE ... ADD COLUMN`，表不存在就跳过（新库由 `schema.sql` 直接建出带列的表）。用 `EntityManagerFactoryDependsOnPostProcessor` 保证它早于 Hibernate 的 `validate`。以后的加列都走这里。
- `Employee` 实体加 `communityJoinDate`（`@JdbcTypeCode(SqlTypes.TIMESTAMP)`，和 `joinDate` 同样处理）。
- `dept` 取自领域频道名，员工数按"幂律"分布到各领域（有的领域人多、有的人少，权重 `1/(i+1)^0.5`，领域顺序随机）。
- **加入日期的分布**：约 45% 是老成员（`历史开始日 − 1~730 天`）；其余新成员在 `[历史开始日, 历史结束日 − 14 天)` 内均匀加入。开启博主画像时，RISING 员工在历史结束日前 21–25 天加入，其他非 RANDOM 画像都是老成员，保证它们原有的登录规划不被打破。
- **任何事件都不能早于加入日期**：登录、浏览、点赞、评论、转发、收藏、发帖。

## 4. 行为模型

新增纯函数式的 `ActivityModel`（`simulator` 包，带单元测试），把"谁在什么时候活跃"集中在一处，历史回填和实时模拟共用同一套概念。

**员工画像 `EmployeeProfile`**（只存在于模拟过程中，不落库；后续的沉默读者等分析必须从行为日志里推导，不能读这些标记）：

| 字段 | 含义 |
|---|---|
| `persona` | 原有博主画像 STAR/RISING/CHURNING/DORMANT/RANDOM |
| `archetype` | RANDOM 员工的留存分型：常驻 30% / 偶尔 40% / 淡出 30% |
| `lurker` | 沉默读者，约 35%（STAR、CHURNING 画像除外）：只浏览，不点赞/评论/转发/收藏 |
| `propensity` | 活跃倾向，幂律 `1/(rank+1)^0.7`，决定被选作浏览者的概率 |
| `fadeStart/fadeLength` | 淡出型的衰减起点（加入或历史开始后 0–60 天）和长度（30–90 天） |

**每日活跃概率** `dailyActivity(profile, day)`：加入日之前为 0；常驻 0.7；偶尔 0.10；淡出型 0.7 随后线性衰减到 0；周末乘 0.35。画像员工：STAR 0.8、CHURNING 0.8（历史结束前 60 天起为 0）、RISING 0.15、DORMANT 0.03（历史结束前 120 天起为 0）。

**时间分布**：一天内的小时有权重（上午 9–11、下午 14–17 为高峰，午休和晚上低，凌晨极低）；周末整体乘 0.35。通过拒绝采样实现，最多重试 10 次，之后接受候选值。

**回填的改动：**
- **登录**：RANDOM 员工从 `max(加入日, 历史开始日)` 到历史结束日，每天按活跃概率抽一次；使用独立随机流，不扰动主随机序列。画像员工的登录规划（`PersonaLoginPlanner`）不变。
- **浏览**：每篇内容的浏览数不变（`1 + popularityWeight × 50`），但时间改成半衰期约 2 天的截断指数衰减（截断在发布后 30 天），再经周末/小时拒绝采样；浏览者按"活跃倾向 × 当天活跃概率"加权抽取，且必须已加入社区；约 70% 的浏览来自内容所属领域的员工，没有合格人选时退回全体，仍没有就跳过这次浏览。
- **互动**：点赞/转发/收藏/评论只发生在非沉默读者身上；为了让总量大致不变，各概率乘 1.5（点赞 0.15、转发 0.075、收藏 0.045、评论 0.12）。评论点赞者同样要求已加入且非沉默读者。
- **发帖**：内容的作者先确定，再确定发布时间，发布时间不早于所有作者的加入日；内容的频道以 70% 的概率落在第一作者所在领域，其余随机领域。

**实时模拟**：`RealtimeEventPlanner` 每批只在"已加入社区"的员工里选演员（`communityJoinDate` 为空视为已加入，兼容旧数据）。
