# 模拟数据校准 · 设计方案

- 日期：2026-10-06
- 状态：已实现（实施计划见 [模拟数据校准](../plans/2026-10-06-simulation-calibration.md)）
- 前置依赖：路线图 10–16 和计划 17 已实现。本计划不新增分析功能，只让演示数据的**量级、结构和时间规律**可信，让已有的分析页能给出有意义的结论。

## 1. 背景：排查发现的问题和根因

对演示库（1000 员工、100 账号、1500 篇内容，2025-03-01 ~ 2026-09-05）做了全面排查。比例类参数（来源占比、点击率、周末效应、停留）基本合理，下面是不合理的部分和**代码里的根因**：

| # | 现象 | 根因 |
|---|---|---|
| 1 | 全库只有 9067 次浏览，登录却有 13.5 万次（每次登录 0.07 次浏览）；每篇内容 PV 中位数 5、最大 62；24% 的人从没浏览过；互动率 32% | 回填按"每篇内容 `2 + 60·热度^0.4` 次浏览"生成，浏览与受众规模、登录行为完全脱钩；互动概率是"每次浏览"的固定值，PV 少所以互动占比高 |
| 2 | 2026-08 加入 108 人（常态 10–20），8 月内容 261 篇、发帖 315 条（常态约 100） | `PersonaAssigner` 按比例分画像：STAR 10%、RISING 10%、CHURNING 10%、DORMANT 20% = **一半员工是画像员工**；RISING 全部在历史结束前 21–25 天加入 |
| 3 | 31% 的人 115 天前就停止登录且不回来，日活 7–8 月从 276 降到 216 | DORMANT 20%（共 8 次登录后沉默）+ CHURNING 10%（结束前 60 天停止）+ "淡出型"占 RANDOM 的 30%，且淡出起点都在加入后 0–60 天、永不回流 |
| 4 | 最后一天（09-04）登录 335 次，常态约 215–260，"区间末日 DAU"偏高 40% | RISING 画像固定在 `end−1` 登录一次，100 人叠加 |
| 5 | 历史结束后（09-05 起）仍有浏览，最近活跃日被拖到 09-28，9 月月均日活 69 | 浏览发生在内容发布后最多 30 天，会越过历史结束日 |
| 6 | 登录周末/工作日 0.73（设计是 0.35） | 画像员工（STAR/CHURNING）的登录规划没有乘周末因子 |
| 7 | 关注人均 2 个、账号粉丝中位 14；账号内容数很均匀；创作者留存全是 100%；首次发帖（中位 4 天）比首次浏览（24 天）还早 | 关注数 `2 + 10×倾向` 而倾向是幂律、均值很小；账号和被关注账号都均匀随机抽；内容的作者发布时间只要求不早于加入日 |
| 8 | KOL 明星占 25%、流失预警 135 人 | 五分位打分的结构性结果（名单 1000 人 ≈ 全员，前 20–25% 平均分 ≥ 4）；流失预警多是 CHURNING 画像（10%）造成 |

## 2. 目标与验收标准

演示数据（1000 员工）校准后必须同时满足（"实测"在计划里逐条验证并写进偏差记录）：

| 指标 | 验收范围 |
|---|---|
| 总 PV | 20–35 万；每篇内容 PV 中位数 ≥ 50；零 PV 内容 < 5% |
| 登录过的员工里至少浏览过一次的 | ≥ 90% |
| 互动（赞/评论/转发/收藏）/ PV | 2–5% |
| 日活 / 成员 | 20–30%；**最后 7 天内没有单日超过前 7 天均值的 1.15 倍**；7 月相对 3 月的日活降幅 ≤ 15% |
| 每月新成员 | 10–25，没有任何一个月超过中位数的 2 倍 |
| 登录周末 / 工作日（日均） | ≤ 0.5 |
| 历史结束日之后的浏览 | 0（最近活跃日 = 历史结束日前一天） |
| 来源占比 | 分享 40%、综合入口 15%、搜索 10%、自主入口 2%，容差 ±3 个百分点（保持不变） |
| 各入口点击率 | 与设定一致（保持不变） |
| 人均关注账号数 | 5–10；粉丝最多的账号 ≥ 中位数的 5 倍 |
| 创作者里全期只发 ≤ 3 篇的 | ≥ 40% |
| 创作者第一次发帖之前已有过浏览的 | ≥ 90% |
| 回填耗时 | ≤ 5 分钟；所有分析接口 < 2 秒 |

## 3. 设计

### 3.1 浏览改为需求驱动（解决 #1、#5）

**浏览由"谁登录了"产生，不再由"内容有多热"产生。**

- 回填顺序改为：先规划全部登录 → 再按登录生成浏览 → 再生成互动。
- 每个登录日产生 `Poisson(λ × m)` 次浏览，λ = `SimulationConfig.viewsPerActiveDay`（新参数，默认 **2.0**，一个可调旋钮），m 是与活跃倾向正相关、均值为 1、范围 0.3–4 的倍率。浏览时刻 = 登录时刻 + 0–4 小时（不跨天），因此保留上班时段规律；不会再有历史结束日之后的浏览。
- 内容选择：候选 = 此刻之前 30 天内发布的内容；权重 = `热度^0.6 × 0.5^(内容年龄/2天)`；约 70% 的浏览先限定在浏览者所属领域的候选里（没有候选就退回全体）。
- 来源抽样保持不变（`SourceSampler` 的占比和退回规则），改成针对"已确定的浏览者"：关注入口只在该员工当时关注的账号的内容里选；视频入口只选视频；自主入口限定在选定的领域；退不出就退回推荐。
- **曝光**：点击对应的"已点击曝光"不变；未点击的曝光，浏览者改为从**当天登录过的员工**里随机挑（70% 优先同领域），不再逐条做全员加权抽样（那样 80 万条曝光会慢几个数量级）。
- **写入**：新增 `ViewBatchWriter`，用 JDBC 批量写 `pv_log`、`impression`、`active_action_log`（VIEW）、`search_log`、`points_ledger`（浏览者的主动 VIEW 积分 + 作者的被动 CONTENT_VIEWED 积分，行为与 `BehaviorEventGenerator.generateView` 逐行一致）。评论需要主键，互动量只占 PV 的几个百分点，仍走现有 JPA 路径。
- **互动概率**：去掉 `INTERACTION_BOOST`，改为赞 3%、评论 0.5%、转发 0.6%、收藏 0.5%（按每次浏览，沉默读者不互动），综合约 2.5–3.5%。回复、评论点赞的比例保持。
- 预期体量：约 27 万 PV、80 万曝光、60 万积分流水，合计比现在多约 200 万行；`viewsPerActiveDay` 调到 1.0 可以减半（验收时如果性能不达标就用它兜底，并在偏差里说明）。

### 3.2 画像与留存（解决 #2、#3、#4、#6）

- **画像比例缩小，且每类至少 2 人**（小规模测试仍能覆盖所有画像）：STAR 3%、RISING 2%、CHURNING 3%、DORMANT 5%，共约 13%（1000 人时 30/20/30/50）。
- **RISING**：加入日分散在历史结束前 21–60 天；登录从加入日起每天约 20% 概率（乘周末因子），并保证至少 2 次、最近一次落在结束前 1–3 天的随机一天（不再固定 `end−1`）。
- **STAR、CHURNING 的登录乘周末因子**（#6）。
- **RANDOM 留存分型**：常驻 30%、偶尔 50%、淡出 20%（原 30/40/30）。
- **淡出起点**均匀分布在 `[开始活跃日, 历史结束−30天)`（原来是加入后 0–60 天，全部挤在最前面），淡出持续 30–90 天；其中 30% 的淡出者在沉默 30–120 天后以"偶尔"的水平**回流**（`EmployeeProfile` 加可空的 `returnDay`）。
- **老成员比例** 45% → 70%：RANDOM 员工里 70% 是历史开始前的老成员，新成员月均加入约 14 人，和现在的常态相当；加上画像比例缩小后，总量仍是约 26% 新成员。

### 3.3 关注、账号、创作者的长尾（解决 #7）

- **关注数**：`4 + round(30 × 倾向^0.6)`，人均约 7；被关注的账号按幂律（账号随机排名，权重 `1/(k+1)^0.8`）挑选，仍保持 70% 偏向同领域。
- **内容归属账号**按幂律（`1/(k+1)^0.8`）挑选而不是均匀：头部账号发帖上百篇，尾部账号只有几篇，自然产生"发一两篇就停"的创作者。
- **内容发布时间** 不早于作者加入社区日期 + 7 天（历史开始前就加入的老成员不受影响），保证作者先有浏览再发帖。

### 3.4 KOL（解决 #8，只做数据侧）

- **不改 KOL 算法**：明星占比高是五分位打分的结构性结果，名单大小决定"头部"的含义。画像缩小后，流失预警（CHURNING 3%）会明显减少。
- 校准完成后实测 KOL 分布：如果明星 > 15%，把演示的 `analytics.kol.top-n` 降到 400 并确认"成长潜力新人"等分层仍然出现；实测结果和最终取值写进偏差记录。
- 分析侧（创作者阶梯、告警中心）不改。

### 3.5 小的分析侧改动

- 留存同期群（读者分析、创作者留存）里人数 < 5 的同期群整行置灰，并在说明里提示"人数很少，比例会剧烈波动"（`ChannelDiagnoser` 已有最小样本门槛，PV 放大后自然生效）。
- README"已知限制"补充：模拟数据量级、`viewsPerActiveDay` 旋钮、实时模拟器（Kafka）的事件速率不随它变化。

## 4. 不改的东西

- 实时模拟（Kafka 流水线）的速率和结构；数据表结构；任何分析接口的口径。
- 来源占比、点击率、停留分布、周末/小时规律的常量（排查时是合理的）。
- KOL 打分和分层算法。

## 5. 测试

- 纯函数：`PersonaAssigner`（比例、至少 2 人、总数守恒）、`PersonaLoginPlanner`（RISING 的新规划、STAR/CHURNING 周末因子）、`ActivityModel`（淡出分散、回流）、新的 `ViewPlanner`（Poisson 总量、浏览时刻在登录之后同一天、内容候选窗口、来源约束、关注入口只选关注账号、同领域占比）、`FollowPlanner`（人均关注、头部集中）、账号幂律选择。
- 仓库/批量写入：`ViewBatchWriter` 写入的行与 `generateView` 逐行一致（pv、曝光、主动行为、积分流水）。
- 集成：新增 `CalibrationIT`（80–200 员工的小回填，按第 2 节验收表里能在小规模验证的项逐条断言）；`HistoricalBackfillRealismIT`、`HistoricalBackfillBehaviorIT`、`HistoricalBackfillPersonaIT`、`KolEndToEndIT`、`BloggerProfileEndToEndIT` 按新画像比例和新登录规划调整，如实说明。
- 真实环境：重建全栈、`seed-demo.sh`，用 SQL 对第 2 节验收表逐项实测，量回填耗时和各分析页接口耗时，`smoke-test.sh` 通过，浏览器走查创作者、用户、读者、驾驶舱、竞赛榜、KOL 几个页面的数字是否合理。

## 6. 风险

- **体量**：约 200 万额外行，回填会从约 1 分钟变成几分钟，分析接口可能变慢。兜底：调低 `viewsPerActiveDay`，或补索引（`pv_log(viewer_employee_id)` 等），都在验收时量化。
- **测试数据变化**：所有依赖旧分布的 IT 断言要调整；调整原则是"保留断言要验证的业务含义，只改数字"。
- **KOL 页面**：画像比例变了，各分层人数会变，需要实测确认五个分层都还有人。

## 7.1 实测结果与实现时的偏差

**验收表实测**（演示库：1000 员工、100 账号、1500 篇内容，2025-04-01 ~ 2026-10-05，`viewsPerActiveDay` = 2.0）：

| 指标 | 校准前 | 校准后 | 结论 |
|---|---|---|---|
| 总 PV | 9,067 | 263,870 | ✓ |
| 每篇内容 PV 中位数 / 零 PV 内容 | 5 / 0 | 134 / 0 | ✓ |
| 登录过的人里浏览过的 | 76% | 100% | ✓ |
| 互动 / PV | 约 37% | 3.27% | ✓ |
| 来源占比（分享/入口/搜索/其他） | 40.3/16.5/9.6/33.6 | 39.9/17.1/10.1/32.9 | ✓ 保持 |
| 各入口点击率 | 与设定一致 | 与设定一致 | ✓ 保持 |
| 日活 / 成员 | 约 25% | 约 27% | ✓ |
| 最后一天日活相对前一周 | 357 vs 约 215–260 | 295 vs 271–285 | ✓ 没有尖峰 |
| 日活走势（首月 → 最后一整月） | 276 → 216（掉 22%） | 约 229 → 约 240（没有下滑） | ✓ |
| 登录周末 / 工作日 | 0.73 | 0.36 | ✓ |
| 历史结束日之后的活动 | 有（拖到 +24 天） | 0 | ✓ |
| 月新成员（最大月 / 中位数） | 108 / 15（7 倍） | 31 / 15（2.07 倍） | ≈ 略高于 2 倍，见下 |
| 人均关注账号 / 最多粉丝÷中位数 | 2 / 约 2 | 6.8 / 7.8 | ✓ |
| 创作者里全期发帖 ≤ 3 篇 | 约 3% | 13%（≤ 5 篇 29%，中位数 8 篇） | ✗ 未达 40%，见下 |
| 创作者首次发帖前已有浏览 | 首发耗时中位 4 天（比首次浏览还早） | 87%（排除历史开头两周的老成员 94%） | ≈ 基本达标，耗时中位 24 天 |
| 回填耗时 / 分析接口耗时 | 约 1 分钟 / < 1 秒 | 约 3 分 30 秒 / < 1 秒 | ✓ |
| 同领域浏览占比 | — | 61% | ✓（旧测试门槛 55%） |

**偏差与取舍：**

- **创作者"一次性作者"占比没有达到 40%。** 1500 篇内容分在 100 个账号里，平均每个账号 15 篇，幂律（指数 0.8）只能让尾部账号发 1–3 篇；要让一半创作者只发一两篇，需要账号数明显多于创作者数。需要时把 `ACCOUNT_COUNT` 调到 200（尾部会有约 40% 的账号 ≤ 3 篇，创作者会增至约 200 人）；默认仍是 100，没有擅自改。
- **月新成员最大月是中位数的 2.07 倍**（2026-08 的 31 人）：RISING 画像的加入日分散在历史结束前 21–80 天（原计划 21–60 天，放宽后仍有一个月偏高）。
- **RISING 画像的每日登录概率从计划的 20% 改成 12%**：20% 时它们的登录频次和积分都进了前几档，被 KOL 判成明星，落不进"成长潜力新人"；12% 才符合"最近才冒头、频次和积分偏低"。
- **KOL 名单人数（演示）取 600。** 实测同一份数据：1000 人时明星 28%、成长潜力新人 20 人；500 人及以下"成长潜力新人"消失（积分太低进不了名单）；600 人时六个分层都有（明星 165 人 = 16.5%、稳定 143、沉寂 159、观察 75、流失预警 48、成长潜力新人 10），明星仍略高于 15%，这是五分位打分的结构性结果。`docker-compose.yml` 里用 `ANALYTICS_KOL_TOP_N`（默认 600）覆盖，`application.yml` 里仍是 1000（企业规模的设计值）。
- **演示数据的历史结束日改为"今天"（不含）**：浏览由登录产生，不再越过结束日，原来"早于今天 30 天"的限制没有必要了，首页和各周期的"最近已结束周期"不会再落在一个只有 4 天数据的月份上。`seed-demo.sh`、前端回填默认值同步修改。
- **回填按月分批**：先试过一次性规划全部浏览，数据库容器在虚拟机内存紧张时被重启；改成"规划这个月 → 批量写入 → 生成互动 → 释放"，内存只和一个月的量有关。
- **清空旧数据改用 JDBC 批量 DELETE**：演示库有 26 万浏览、80 万曝光、70 万积分流水，JPA 的 `deleteAll()` 会把它们逐条读进内存，后端容器被 OOM 杀掉（容器里点"清空并回填"同样会崩）；这是校准前就存在的隐患，数据量变大后才暴露。
- **后端容器的 JVM 内存默认从 75% 降到 50%**（`docker-compose.yml`）：4GB 的 Docker 虚拟机里 75% 会把数据库挤垮。
- **没有改的**：KOL 算法、来源/点击率/停留常量。实时模拟器当时没改，后来在"后续优化"里改成了同一个事件模型（见下）。
- **后续优化（同日）**：偶尔型登录率 0.10 → 0.05（月活 82% → 71%）；实时模拟器按同一个模型发事件（每次登录约 2 次浏览、互动约占浏览的 3%，演员按最近 90 天登录次数加权，内容按热度 × 新鲜度挑，约 70% 看本领域）；告警每天 7 点自动重算；用户列表、创作者排行、沉默读者名单可导出 CSV；新增 GitHub Actions CI。

**校准后仍可以关注的现象**（不影响本计划验收，留作后续）：月活 82%（偶尔型用户 30 天内几乎都登录过）、黏性 0.28；沉默读者占 39%（沉默读者本来就占 RANDOM 员工的 35%）；价值分层"核心"约 30%。

## 8. 明确不做的范围（Out of Scope）

- 实时模拟器的速率校准；真实姓名；入口位置、置顶位、不感兴趣（已确定不做）。
- 预计算/缓存分析结果、更大规模（>1 万员工）的性能优化。
